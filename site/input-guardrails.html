Input Screening

Two layers screen every prompt before the main model sees it: a free, instant regex pass for unambiguous injection attempts, and a purpose-built guard model for the cases a pattern can't judge. A flagged prompt never reaches Ollama at all, which makes this structurally the strongest guardrail in the system.

Builds on: the composed guardrails. Needs: granite4.1-guardian:8b pulled (optional). Full code: checkpoint chapter 9, the complete Part 2 system.

Two problems wearing one name

"Prompt injection" covers two attack surfaces that deserve separate threat-model entries. The famous one is the user's own prompt: "ignore your previous instructions," jailbreak personas, system-prompt extraction. The subtler one, and for RAG systems the more real one, is injection through retrieved content: your knowledge base is attacker-controlled input, and a document containing "disregard your rules" gets retrieved by an innocent query wearing the authority of a trusted tool result.

This page defends against the first. The second gets named honestly rather than solved: this system's corpus is one PDF you control. If your production corpus accepts uploads, wikis, or emails, retrieved-content injection belongs on your risk register with real mitigations. Knowing which problem you've solved, and which you've only named, is the discipline.

Pass 1: the pattern list

INJECTION_PATTERNS = [
    (r"ignore (all |any |the )?(previous|prior|above|preceding) instructions", "instruction override"),
    (r"disregard (all |any |the )?(previous|prior|above|preceding) (instructions|rules|prompt)", "instruction override"),
    (r"you are (now|no longer) (a|an)\b", "role override"),
    # A bare "pretend (you are|to be)" match would false-positive on
    # harmless roleplay like "pretend to be a pirate and tell me a joke."
    # Require the roleplay request to be paired with safety-bypass language.
    (r"pretend (you are|to be)\b.{0,60}(no (restrictions|rules|filters|guardrails)|"
     r"without (any )?(restrictions|rules|filters|guardrails)|unfiltered|no limits)", "role override"),
    (r"no (restrictions|rules|filters|guardrails)", "safety bypass"),
    (r"(reveal|show|print|repeat) (your |the )?(system prompt|instructions)", "system prompt extraction"),
    (r"what (are|is) your (system prompt|instructions|rules)", "system prompt extraction"),
    (r"\bDAN\b|do anything now", "known jailbreak persona"),
]


def _check_prompt_injection(user_prompt: str) -> list:
    """Runs against untrusted input, before the prompt joins any message list."""
    hits = []
    for pattern, label in INJECTION_PATTERNS:
        m = re.search(pattern, user_prompt, flags=re.IGNORECASE)
        if m:
            hits.append((label, m.group(0)))
    return hits
The instructive pattern

The fourth one, because of what it doesn't match. A bare pretend (you are|to be) blocks "pretend to be a pirate and tell me a joke": harmless roleplay, zero jailbreak intent. The narrowed version requires paired safety-bypass language within 60 characters, because that pairing is what distinguishes an attack from whimsy. Every pattern should encode a claim about what attacks look like, not a vibe about suspicious words.

Be honest about this layer: a determined attacker routes around fixed patterns with paraphrase, and false positives exist at the margins ("ignore the store hours for a second..." trips the first pattern). The claim is "blocks the obvious stuff, for free, deterministically." A production system facing adversarial public traffic wants a learned classifier with a lower false-positive rate.

Pass 2: a model whose only job is judging

The pirate prompt motivates the second layer: too ambiguous for a regex, obvious to anything that understands intent. Granite Guardian is IBM's model fine-tuned for exactly one job, judging text against named harm criteria (jailbreak, violence, social_bias, and others). Not a chat model asked to self-police: a specialist.

The layering economics matter as much as the model: regex first because it's free and deterministic, Guardian only on prompts that already cleared it.

GUARD_MODEL = "granite4.1-guardian:8b"
USE_LLM_GUARD = True  # set False to skip this pass (e.g. model not pulled yet)


def _check_prompt_injection_llm(user_prompt: str, criteria: str = "jailbreak") -> dict:
    """"flagged" True means Guardian scored it <score>yes</score>."""
    try:
        response = client.chat.completions.create(
            model=GUARD_MODEL,
            messages=[
                {"role": "system", "content": criteria},
                {"role": "user", "content": user_prompt},
            ],
        )
        raw = response.choices[0].message.content or ""
        match = re.search(r"<score>\s*(yes|no)\s*</score>", raw, flags=re.IGNORECASE)
        flagged = bool(match) and match.group(1).lower() == "yes"
        return {"flagged": flagged, "raw": raw, "error": None}
    except Exception as e:
        # Fail open: couldn't get a verdict, don't block on that basis alone.
        return {"flagged": False, "raw": "", "error": str(e)}

Protocol: criteria name as the system message, text under judgment as the user message, verdict in a <score>yes/no</score> tag. Verify the tag against your live model's actual output before trusting the parse; structured-output contracts with models are contracts with a counterparty that didn't sign.

Fail open, deliberately

If the Guardian call errors (model not pulled, Ollama down), this logs a warning and lets the prompt through on the regex verdict alone. Right for a single-user local system; a production deployment facing real attackers should probably fail closed. Neither answer is universal. What's non-negotiable is choosing deliberately and writing the choice down.

Both passes run at the very top of run_agent, before the message list is even built; a flagged prompt returns a block message naming which layer fired and inviting a rephrase (false positives deserve a path forward). Wiring in the chapter 9 checkpoint.

The honest ledger on LLM-as-judge

It costs a second model call's latency per screened prompt. It's nondeterministic, which makes offline testing genuinely harder. And the judge itself ingests attacker text, so a crafted prompt could in principle manipulate the judge too. The trust boundary moves; it doesn't disappear. Layering is what makes it acceptable: deterministic pass in front, semantic pass behind, each covering the other's blind side.

With this page done, count the layers on a single question: two input screens, a calibrated retrieval threshold, a grounding-hardened prompt, two termination backstops, and a citation verifier on the way out. Each one holds a judgment the model would otherwise hold alone.

Guardrails That Compose

Two individually correct guardrails produced a new failure between them: an agent that couldn't stop searching. This page builds the structural fixes (a tools=None backstop, an unconditional final-turn rule, a chunk-length floor, a versioned cache key) and teaches the lesson that guardrails must be tested as a system, not as components.

Builds on: the calibrated threshold. Full code: checkpoint chapter 8.

Two correct guardrails, one new failure

The problem

Before the threshold existed, the model handled no-answer questions tolerably: it read three weak chunks, noticed they didn't answer, and said so. After the threshold, it receives a clean rejection note and sometimes responds by searching again. New phrasing, same rejection, until the turn budget dies and the user gets "Hit max_turns without a final answer": strictly worse than before.

The mechanics matter because the pattern recurs in every layered system. The threshold is correct: those chunks were weak. The model's reasoning isn't crazy: an empty result reads like "bad query," and reformulating is what diligent searchers do. Each component behaves. The failure lives in the interaction: the threshold changed what "no answer" looks like, from visible-but-weak chunks into a repeatable rejection that invites retry. Nobody wrote a retry loop. The system grew one.

Takeaway

Testing guardrails in isolation validates components, not the system. The threshold passed its calibration table; the citation check passed its cases; the infinite loop lived between them, invisible to both.

The prompt request, and why it's not enough

First response, per the standing pattern: a "search discipline" rule in the system prompt (stop after two fruitless searches, answer with what you have). Clear rule, explicit trigger. And the model still, in some runs, sails past it with the instruction sitting right there in context.

Run the design test: if the model ignores this sentence, what catches it? Nothing. So: structure.

The structural backstop, twice

The API accepts tools=None, and a model with no tool declarations cannot emit a tool call; the only legal move is text. That enforcement gets used twice: count consecutive empty searches and take tools away at two, and, unconditionally, never offer tools on the final turn.

    retrieved_pages = set()
    consecutive_empty_searches = 0  # +1 per empty search result, reset on success

    for turn in range(max_turns):
        ...
        # Empty-search backstop AND the unconditional final-turn rule:
        force_text_only = consecutive_empty_searches >= 2 or turn == max_turns - 1
        tools_for_this_turn = None if force_text_only else TOOL_SCHEMAS
Why two rules

The counter has a blind spot: it only advances on empty results, and in a topically coherent corpus, reformulated searches rarely come back empty. A model hunting for the unanswerable half of a two-part benefits question keeps matching semi-relevant chunks in the generically-related score band, each non-empty result resets the counter, and every turn burns while the real answer sits retrieved in the transcript. The final-turn rule triggers on turn number alone, which no pattern of results can dodge: the last turn is always an answer turn.

Read the philosophical change: the prompt tried to persuade the model away from the bad option. The backstop removes the option from the menu. Nothing to persuade, nothing to comply with; the model cannot call a tool that wasn't offered, the same way calculate cannot eval arbitrary code. When you need a guarantee, restructure the choice space; don't escalate the rhetoric.

Keep the prompt rule anyway: when the model honors it, the agent concludes a turn earlier. The prompt improves the common case, the counter bounds the known worst case a turn early, and the final-turn rule bounds every worst case including the unimagined ones.

One more piece of structure at the exit: a small model forced into a text-only turn occasionally returns an empty string. Never hand the user a blank answer:

            return message.content or "(the model returned an empty answer)"

The second composition bug: junk chunks

The problem

Very short chunks hit an embedding-normalization artifact: with almost no content to dilute the match, a two-word chunk scores inflated similarity against nearly any query sharing common vocabulary. In this system's testing, a bare "EMPLOYEE HANDBOOK" title fragment scored 0.827 against an unrelated query, above chunks with real content and above any plausible threshold.

Trace the blast radius: the junk chunk clears the threshold, so a should-be-empty search comes back non-empty, so the counter resets, so the backstop never fires. One malformed input at the bottom of the pipeline quietly disarmed a guardrail three layers up. Worse: casual testing showed the backstop "working," because most queries didn't collide with the junk chunk's vocabulary. A guardrail can look validated by luck.

MIN_CHUNK_CHARS = 60   # drop chunks shorter than this before embedding

# _chunk_text's return line becomes:
    return [c for c in chunks if len(c["text"]) >= MIN_CHUNK_CHARS]

Chunk-quality filtering isn't cosmetic cleanup. It's load-bearing for every guardrail whose input is a similarity score.

The stale-cache trap

The problem

Change the chunking logic and rerun: nothing happens. The PDF's bytes didn't change, the content hash matches, ingestion skips, and the junk chunks sit exactly where they were, on disk. The cache is behaving as designed, and its design just silently discarded your fix.

The cache key was wrong from the start: the collection's contents are a function of the PDF and the chunking logic, and the key only covered the PDF. So the logic gets a version number, folded into the hash:

CHUNK_LOGIC_VERSION = 2   # bump when chunking/ingestion logic changes

content_hash = hashlib.sha256(pdf_bytes + str(CHUNK_LOGIC_VERSION).encode()).hexdigest()[:16]
Takeaway

Derived-data caches must key on everything the derivation depends on. File bytes are the obvious dependency; the code that transforms them is the one everyone forgets.

What healthy looks like

Ask something with zero real coverage ("does the company offer a cryptocurrency signing bonus?") and the trace shows the counter path: two below-threshold rejections, then:

  (tools disabled this turn — 2 consecutive empty searches, forcing a final answer)

Ask a two-part question where only half is answerable and you'll likely see the blind-spot path instead: the counter resets on semi-relevant matches, and the final-turn rule closes it out:

  (tools disabled this turn — final turn, forcing a final answer)

Either way, a real answer. Termination isn't hoped for anymore; it's enforced.

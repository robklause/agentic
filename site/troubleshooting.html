Troubleshooting

Organized by symptom, because that's what you have when you arrive here. Each entry: what you're seeing, what's actually wrong, what to do.

Jump to: install · Ollama & models · retrieval · loop & guardrails · MCP

Installation and environment

"Could not find a version that satisfies the requirement" / "No matching distribution found" for mcp

Reads like a network problem. It's your Python version: the mcp SDK requires 3.10+, and pip on an older interpreter reports "no distribution" instead of "Python too old." Run python3 --version; if you see 3.9.x, rebuild the venv with a newer interpreter (python3.12 -m venv .venv). (Setup)

Packages installed fine, but the script can't find them

The venv isn't active in this shell, or your editor points at a different interpreter. source .venv/bin/activate, and in VS Code run "Python: Select Interpreter." which python should answer inside the project folder.

Ollama and models

Connection refused / connection error on any model call

Ollama isn't serving. Run ollama serve (if it's already running as a service, that reports the port in use, which is fine). Confirm the endpoint matches: localhost:11434.

Model-not-found error naming your chat model

The pull didn't finish or the tag doesn't match. ollama list shows what you have; compare character for character against MODEL. Mac users who pulled qwen3.5:9b-mlx while the code says qwen3.5:9b (or the reverse) hit exactly this.

The model answers in text but never calls tools, or hallucinates argument JSON

Not every local model supports tool calling well, and the failure is behavioral, not an error. Before debugging your code, swap in a model documented as tool-call capable (gemma4:12b is a solid alternative) and compare. If gemma calls tools and yours doesn't, the code was never the problem. (Setup)

Long pauses mid-run, especially between the guard-model line and the first agent turn

Model swapping, not a hang. The series rotates three models, and on a machine without room to keep them resident (16GB is the squeeze point), Ollama evicts one to load another, costing seconds per swap. Fix hierarchy: patience; USE_LLM_GUARD = False to drop the guard model from the rotation; a smaller chat model; or more RAM plus a dedicated GPU/APU/NPU. On Apple Silicon prefer the -mlx tags. (Hardware)

Everything works, but the first handbook question takes a minute-plus

First-run ingestion embeds every chunk; that's the printed "may take a minute" doing what it said. Later runs print "already indexed... skipping." If ingestion runs on every start, see the cache entries below.

Retrieval and the vector store

Similarity scores look plausible but results are consistently nonsense

Classic mismatched-embedding-model signature: documents embedded with one model, queries with another, two vector spaces, no error anywhere. Usually appears after changing EMBED_MODEL without re-ingesting. Bump CHUNK_LOGIC_VERSION (or call ingest_pdf(force=True)) and recalibrate the threshold. (Knowledge base)

You changed chunking logic and behavior didn't change at all

The stale-cache trap. The ingest cache keys on PDF bytes plus CHUNK_LOGIC_VERSION; changing logic without bumping the version means the cache correctly concluded nothing changed. Bump it and rerun. (The trap)

Chroma errors after an upgrade, or create_collection says the collection already exists

get_collection can fail for reasons other than absence (an embedding-function config mismatch after a library upgrade is the known one), which is why ingest_pdf deletes unconditionally inside a try/except. If on-disk state is truly wedged, deleting the chroma_db/ directory is safe: nothing in it is the source of truth.

Covered topics get rejected by the threshold, or absent topics sail through

The threshold is calibrated to one document, one chunking, one embedding model; change any and the old number describes a geometry that no longer exists. Rerun calibrate_similarity_threshold() and read the printed table: overlapping classes show up as flagged misclassifications. Also verify your eval labels against the corpus; one mislabeled example poisons the midpoint. (Calibration)

A search returns a title or header fragment with a suspiciously high score

The junk-chunk artifact (a bare "EMPLOYEE HANDBOOK" fragment scored 0.827 in testing). MIN_CHUNK_CHARS exists for this. If you're still seeing it: the filter was removed, the cache is stale, or your document produces junk longer than 60 characters, in which case raise the floor and bump the version. (Junk chunks)

The loop and guardrails

"Hit max_turns without a final answer."

From the backstop page onward this should be unreachable: the final turn never offers tools, so the model must answer in text before the cap expires. If you see it, either you're running an earlier checkpoint (expected there), or the final-turn condition didn't make it into your file. Check that force_text_only includes or turn == max_turns - 1.

The answer is "(the model returned an empty answer)"

The guardrails worked; the model didn't. A forced text-only turn can make a small model emit an empty string, and this fallback stops it rendering as a blank line. If it recurs often, that's a model-capability signal, not a code bug. (Bigger models)

The citation guardrail flags pages on answers that look right

Working as designed; the question is which side is wrong. If the cited page really contains the fact, the model likely knew it from a compacted digest while retrieved_pages was reset. If the page is plausible-but-wrong, you just watched the guardrail do its job. (Verifying citations)

Constant "zero page citations — cannot verify grounding" flags

The model isn't complying with the strict citation format, common with smaller models. Confirm the system prompt includes the full strict-format rule (the p.17 example does real work), and consider whether your model is up to instruction-following at this density.

Legitimate prompts get blocked by the pattern screen

A known false-positive cost ("ignore the store hours for a second..." trips the first pattern). The block message names the matched category; find that pattern and narrow it the way the "pretend" pattern was narrowed, letting ambiguity fall through to the guard model. (Pattern list)

"Granite Guardian check failed, failing open" on every prompt

The guard model isn't reachable: not pulled (ollama pull granite4.1-guardian:8b), or Ollama is down. The system keeps working on the regex layer alone; set USE_LLM_GUARD = False to silence the warnings until you pull it.

Guardian responds but never flags anything, or flags everything

Check the raw output the trace prints against the parser's expectation: a literal <score>yes</score> or <score>no</score>. A different Guardian version with a different output shape parses as never-flagged. Verify against your live model and adjust the regex. (Guard model)

MCP

You ran the server by hand and it just sits there

Correct behavior. A stdio server blocks on stdin waiting for a client handshake; it waits forever when run by hand. Ctrl+C to exit. No output plus no traceback equals a working server. (MCP server)

The agent hangs at startup, before the [mcp] connected line

The client is waiting for a handshake that isn't coming. Usual causes in order: mcp_weather_server.py isn't in the working directory you launched from (the launch recipe uses a relative path); the server crashes on import, so nothing is listening (run it by hand once, expecting silence, not a traceback); or the command in MCP_SERVER_PARAMS doesn't resolve, python3 versus python on Windows being the common case.

MCP tool results arrive as escaped JSON strings inside strings

structured_content came back None and something passed the raw text block through. A plain -> dict server return doesn't populate it; only a Pydantic model return does. _call_mcp_tool handles this by parsing the text block; if you wrote your own client path, add the same fallback. (The gotcha)

Every MCP call is slow and Python processes churn in the process table

The respawn trap: something opens a connection per call (usually asyncio.run(...) at the dispatch site) instead of one for the run. For a stdio server the connection owns the subprocess, so per-call connections mean per-call process spawns. Restructure to the single long-lived async with. (Connection lifetime)

RuntimeError: asyncio.run() cannot be called from a running event loop

Something inside the async call stack called asyncio.run while main was already running under it. Inside async code, await things; asyncio.run belongs in exactly one place, the __main__ entry point.

When nothing here fits

Turn verbose on and read the trace end to end before theorizing: the raw messages, the tool dispatches with their (local)/(mcp) labels, and the guardrail lines tell you what actually happened, which beats any hypothesis about what should have. Then diff your file against the nearest checkpoint. Ten minutes of diff has settled every "but I didn't change anything" in the history of software.

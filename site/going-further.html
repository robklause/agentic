Going Further

What changes when this system leaves your laptop (three lines), and what to reach for in each direction the series deliberately didn't go. A page of doors, each opened far enough to see through.

Builds on: the finished system.

Swapping in a cloud model

Everything here runs through an OpenAI-compatible client pointed at Ollama, so pointing it elsewhere is configuration, not a rewrite:

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],   # a real key now — never hardcode it
)
MODEL = "<model string from OpenRouter's catalog>"

That's the whole migration. What rides along untouched: the loop, all three local tools, the MCP server with its discovery and dispatch, compaction, both input guardrails, the citation verifier, the termination backstops, and the threshold's enforcement. Azure OpenAI and Bedrock work the same way with their OpenAI-compatible endpoints.

Two honest caveats

Embeddings stay local, and that's a feature: your document vectors, vector store, and calibrated threshold stay valid, and your corpus never leaves the machine. Chat to the cloud, retrieval at home, a genuinely good hybrid. Moving embeddings to a hosted model changes vector spaces: re-ingest (bump CHUNK_LOGIC_VERSION) and recalibrate. And the meter is back: every turn resends the conversation, and every guardrail probe costs real money.

The workflow this whole series prepared you for: develop and iterate locally for free, swap three lines for the deployment that needs frontier quality. Keep the local config in a comment; you'll toggle back constantly. And per bigger models, the guardrails all stay.

More MCP servers

One server taught the pattern; the pattern was built for many. Generalizing is bookkeeping: hold several (client, schemas, names) sets, merge the schemas, route by whichever names-set claims a call.

The interesting problems at N servers are architect problems. Name collisions: two servers both exposing search, disambiguated by prefixing or by curating what you forward. Trust tiers: a server you wrote, a vendor's, and something from a community registry don't deserve equal standing, and description text from low-trust servers lands in your model's context, which is an injection surface. Context budget: every discovered tool's schema ships with every model call, so a forty-tool server taxes every turn whether or not the model uses any of them. Curate; don't just connect.

Persisting conversations

run_agent starts fresh every call because messages is built inside it. Real assistants remember. The message list is plain JSON-serializable data, so persistence is structurally easy, but two design points deserve care: compaction becomes essential rather than optional (a conversation living for weeks won't fit any context window), and guardrail state must persist with the transcript. retrieved_pages especially, because a resumed conversation that forgot what it retrieved will flag every citation from yesterday as a hallucination.

Streaming

This series printed answers when they finished, which is right for reading traces and wrong for users watching a spinner. The wrinkle worth knowing before you start: tool calls stream too, arriving as incremental argument fragments you assemble before dispatching. The loop's logic doesn't change, but the tidy "message in, message out" turn structure becomes an accumulation state machine. Budget an afternoon, not an hour.

Multi-agent architectures

Strip the vocabulary away and a "multi-agent system" is agents-as-tools: a coordinator loop whose tool schemas happen to invoke other loops. A researcher agent delegating to a summarizer is run_agent calling something that calls run_agent: one more entry in a dispatch table, one more seam.

Which means everything from Part 2 applies at every level. Each inner agent needs its own termination backstop (max_turns compounds across nesting). The coordinator needs discipline about trusting sub-agent output, since an inner agent's answer is a tool result, exactly as unverified as any other. And the composition lesson applies with interest, because now entire agents are the components interacting in untested ways.

Frameworks: when to adopt one, and how to read one

This series skipped frameworks for visibility, not disdain. You built the loop bare so nothing could hide. That job is done, and adopting a framework now is an ordinary engineering decision you're unusually equipped to make, because every agent framework contains the loop you wrote, wearing different clothes.

The evaluation lens

Reading any framework's docs, ask: Where's the loop, and can I see a turn? Where's the seam between "the model asked for a tool call" and "run it," and can I put my own code there? When the model ignores an instruction, what catches it, structure or a politely worded request? What exactly is in the context each turn, since somebody's compaction policy is running whether or not the docs mention one?

Applied to the current landscape, as of this writing:

LangGraph (the agent-focused core of LangChain) makes the loop explicit as a state graph: your for turn in range(max_turns) becomes nodes and conditional edges, which pays off when the workflow genuinely branches, needs checkpointing mid-run, or requires human approval between turns. Of the majors, its abstraction is the most honest about being a loop.

CrewAI is role-based multi-agent: define a crew with goals and tool sets and let them collaborate. Reread multi-agent above and you see through it immediately: agents-as-tools with personas, fast to prototype, with every question about inner-loop termination and sub-agent trust still live.

Microsoft's tooling (AutoGen and Semantic Kernel, converging into the Microsoft Agent Framework) targets multi-agent conversation patterns and enterprise .NET/Azure shops. If your organization is a Microsoft shop, this is the gravity well you'll evaluate whether you like it or not, so evaluate it with the lens rather than the deck.

Pydantic AI is the lightweight one: typed, schema-validated agent responses. You already believe in its core idea; it's normalize-at-the-boundary productized, with the "whatever happens, the caller sees the promised shape" contract enforced by types.

Vendor SDKs (OpenAI's Agents SDK, Anthropic's Claude Agent SDK) are the loop plus handoffs plus platform tooling, thinner and easier to see through. LlamaIndex sits beside all of it as the retrieval specialist: the knowledge base page as a mature product, with fifty chunking strategies where you wrote one.

What a good framework buys you is the commodity plumbing this series waved past: retries and backoff, streaming assembly, persistence, checkpointing, provider abstraction, and observability. That last one deserves its own line: "the trace is the product" grows up into tracing platforms (LangSmith, Langfuse, OpenTelemetry-based tooling), and once an agent has users, searchable production traces stop being optional. There's a parallel ecosystem for guardrails too (NVIDIA NeMo Guardrails, Guardrails AI, Meta's Llama Guard as a sibling of Granite Guardian); evaluate those exactly as input screening taught: what's deterministic, what's a model judging, and what happens when the judge is unavailable.

What a framework costs you is what this series just spent fifteen pages giving you: nothing hides in a file you wrote, and something always hides in a dependency. You'll debug through someone else's abstraction at the worst possible moment, and agent frameworks are young enough that major-version churn is a real line item.

The heuristic

Adopt a framework when your needs are boring in the best sense: checkpointing, streaming, tracing, retries, the things every agent needs and none differentiates on. Stay bare, or thin, when the control flow is the product. Either way, keep the guardrails yours: the risk ledger is specific to your risk profile, and no dependency ships it. Framework names will churn. The four questions won't.

Evals: growing the ten-query habit

You already built an eval harness. The labeled eval set is real: labeled cases scored by the live pipeline with misclassifications flagged. And the designed probes in the standard run (the crypto question for the backstop, the injection string for pass 1, the pirate for pass 2) are behavioral test cases in everything but name.

The production discipline is that habit at scale, run automatically: suites of labeled inputs with expected behaviors, executed against the real system on every change, because a prompt edit is a code change and deserves regression tests. The whack-a-mole problem is why this matters more for agents than for ordinary software: fixing one unstated-negative case can quietly un-fix another, and without a suite you find out from a user.

Tooling so you don't build the runner: promptfoo (config-driven suites, comfortable in CI) and DeepEval (pytest-style, evals as ordinary test functions) are the established starting points, and the tracing platforms above score live traffic against the same checks. One caution carries over intact: many eval metrics are LLM-as-judge underneath, with everything that implies. Prefer deterministic assertions wherever the behavior allows one ("the answer contains a p.NN citation," "the blocked-prompt response names the layer that fired"), and spend model-judged scoring on questions that genuinely require judging meaning. That's the principle, applied to the tests instead of the system.

Where to keep reading

Primary sources, deliberately few. modelcontextprotocol.io for the MCP spec and SDKs; the spec is short enough to actually read, and after the client page you'll recognize everything in it. ollama.com/library for new local models, where tool-calling support is called out per model; both your chat and embedding models will be superseded within months, and the swap procedure is this page's first section minus the API key. IBM's Granite Guardian model cards document the full criteria list beyond jailbreak.

What you actually built

A set of reflexes. An agent is a loop you can read. A tool is a judgment taken out of the model's hands. A guardrail is code where a request would fail silently. A protocol is a seam you already had, standardized. Every system you evaluate from here sorts itself against those four sentences faster than any slide can talk.

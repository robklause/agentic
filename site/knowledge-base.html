Adding a Knowledge Base

RAG is a tool, exactly like a calculator: the model calls search_knowledge_base("PTO days"), your code returns relevant passages from a real document, and the model answers from those instead of from memory. This page ingests a 58-page PDF into ChromaDB and exposes semantic search to the agent.

Builds on: the two-tool agent. Needs: nomic-embed-text pulled, chromadb + pypdf installed, and the PDF (download, 92KB). Full code: checkpoint chapter 4.

The problem worth solving

The problem

Ask the agent "how many PTO days do new employees get?" and it answers. Confidently. From nothing. It's seen thousands of handbooks in training, so it produces a plausible number with no connection to your handbook. Not ignorance: fluent fabrication.

The entire sophistication of RAG lives in one question: how does your code decide which passages are relevant? Keyword matching fails silently: users ask about "vacation days," the document says "PTO," zero overlap, zero results. Users don't share vocabulary with documents. They share meaning.

Embeddings in one paragraph

An embedding model converts text into a vector (a long list of numbers) built so texts with similar meaning land near each other. "Vacation days" and "paid time off" produce nearby vectors despite sharing no words. Relevance becomes geometry: embed the query, embed every chunk, and the nearest chunks by cosine similarity win. That's semantic search, and nomic-embed-text does exactly this one thing.

The classic RAG bug

Documents and queries must be embedded with the same model. Two models means two vector spaces, and distances between them are meaningless. Nothing errors; scores still look like numbers. The fix is structural: route both through one function.

class OllamaEmbeddingFunction(EmbeddingFunction):
    """Chroma calls this both when documents are added and when a query
    runs — using the same function for both is what keeps them comparable."""

    def __init__(self) -> None:
        pass  # no state

    def __call__(self, input: Documents) -> Embeddings:
        return [
            client.embeddings.create(model=EMBED_MODEL, input=text).data[0].embedding
            for text in input
        ]

Register this class with the Chroma collection and Chroma itself calls it on both sides. Same function, same model, same vector space, enforced by structure rather than discipline.

The ingestion pipeline

Four steps: extract, chunk, embed, store. The constants that shape it:

EMBED_MODEL = "nomic-embed-text"
KB_PDF_PATH = "Marlow_and_Sage_Handbook.pdf"
CHROMA_DB_DIR = "./chroma_db"     # persisted on disk — ingest once, reuse after
COLLECTION_NAME = "handbook"
CHUNK_SIZE = 1000                 # target characters per chunk
CHUNK_OVERLAP = 150               # characters carried into the next chunk

The full pipeline is ~120 lines in the chapter 4 checkpoint. The decisions that matter, per step:

Extraction (pypdf) keeps page numbers with the text, because every chunk carries a p.NN source tag, and those tags become a guardrail's raw material. It also strips the running header the PDF repeats on every page: a string on all 58 pages is pure noise that dilutes every chunk's vector toward the same average. Swapping in your own PDF? That strip regex is the line to change.

Chunking packs whole paragraphs into ~1000-character chunks instead of slicing at exact counts, so each chunk stays a coherent unit of meaning. The 150-character overlap exists for facts that straddle a boundary; without it, a sentence cut in half is invisible to search from both sides.

Ingestion caching: embedding a long document takes a minute-plus, so ingest is skipped when a hash of the PDF (plus a chunking-logic version number) is already indexed. The version number matters more than it looks; the stale-cache trap explains why.

The search tool

def search_knowledge_base(query: str, top_k: int = 3) -> dict:
    """Semantic search over the persistent Chroma collection. Lazily
    ingests the PDF on first call in a process."""
    global _kb_collection
    if _kb_collection is None:
        _kb_collection = ingest_pdf()

    result = _kb_collection.query(
        query_texts=[query],
        n_results=top_k,
        where={"type": "chunk"},  # exclude the cache-sentinel record
    )
    docs = result["documents"][0]
    metas = result["metadatas"][0]
    dists = result["distances"][0]

    results = [
        {"source": meta["source"], "text": doc, "similarity": round(1 - dist, 3)}
        for doc, meta, dist in zip(docs, metas, dists)
    ]
    return {"results": results}

Each result carries three fields, and all three earn their keep later: text is what the model reads, source (like Marlow_and_Sage_Handbook.pdf p.17) is the citation a guardrail will verify, and similarity is the score a calibrated cutoff will filter on.

The loose thread

Right now this returns the top 3 chunks no matter how weak the matches are. When the document has no answer, the model still receives three semi-related passages formatted exactly like a real answer. Part 2 exists because of what models do with that temptation.

The tool joins TOOL_IMPLEMENTATIONS and TOOL_SCHEMAS like any other, and the system prompt gains the matching push: always search before answering policy questions, only state facts from returned chunks, name the source, and say "I don't have that information" rather than guess.

The bill comes due: context bloat

The problem

The chat API is stateless: the full message list is resent every turn. One search returns up to three ~1000-character chunks, and that payload gets resent on every subsequent turn. Two searches in, most of what you ship to the model is stale tool output.

The design

Compaction: collapse older tool exchanges into a one-line digest, keep the system prompt, the original question, and the most recent messages verbatim. It's a trade, not a win: the digest keeps the facts but drops exact wording.

One subtlety worth knowing even if you never touch the code: every tool result message is paired by id to the assistant message that requested it, and a naive slice can strand one half of the pair on the wrong side of the cut. The _compact_history() function in the checkpoint walks the split point to a clean seam first. Message lists look like arrays; they have referential structure.

Run it

Ask something the handbook answers and watch the trace: an ingest line on first run (the skip message forever after), a search call, three chunks with p.NN sources and similarity scores, then an answer citing real accrual numbers from a real document.

Then ask something it doesn't answer ("what's our parental leave policy?") and watch closely. Three semi-related leave chunks come back anyway, each wearing the authority of a real result. What the model does next is the opening problem of Part 2.

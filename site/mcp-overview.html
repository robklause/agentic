Where MCP Fits

MCP (the Model Context Protocol) slots into exactly one seam of the loop you already built: the moment between "the model asked for a tool call" and "run it." Nothing about the control flow changes. What changes is where a tool's definition comes from and where it executes. No code on this page; it's the orientation that makes the next two pages small.

Builds on: the loop and hand-written tool schemas. Next: build a server.

The problem MCP standardizes

Your agent has three tools, and you hand-built both halves of each: the implementation in a dict, the JSON Schema in a list. Fine for three tools you wrote. Now scale it the way an architect has to.

Every team building an agent needs tools for the same systems: Jira, GitHub, Postgres, Slack, the data warehouse. Without a standard, every agent integrates every tool bilaterally, N agents times M tools, each pairing hand-typing schemas and writing glue against a different vendor API. You've seen this movie: it's why ODBC exists, why LSP exists.

MCP's shape: a tool provider ships an MCP server, a process exposing tools over a standard wire protocol (JSON-RPC, over stdio locally or HTTP remotely). Any agent that speaks the protocol as a client can ask "what tools do you have?", get JSON Schema answers, and invoke them. Write the server once; every MCP-speaking agent can use it. The matrix becomes a bus.

One seam, the same seam as always

Your loop does two things with tools today:

# 1. Tell the model what exists: a hand-typed list, sent every turn.
tools=TOOL_SCHEMAS

# 2. Run what it asks for: a dict lookup, called in-process.
impl = TOOL_IMPLEMENTATIONS.get(name)
result = impl(**args)

MCP replaces the source behind each line:

# 1. Tool definitions: discovered at runtime by asking the server.
discovered = await mcp_client.list_tools()

# 2. Execution: invoked across the process boundary.
result = await mcp_client.call_tool(name, args)
The whole claim

Hand-typed schemas become list_tools(). The dispatch dict becomes call_tool(). That's the entire footprint. The model still emits the same tool_calls JSON and neither knows nor cares that a schema was discovered rather than typed, or that a call crossed a process boundary.

Your guardrails don't care either: input screening ran before the loop started, the backstop counts search results wherever they came from, the citation check reads the final answer. Everything from Part 2 rides through untouched.

Hold that sentence and you can evaluate MCP as an architect rather than a reader of press releases: it isn't an agent framework, a reasoning layer, or a competitor to your loop. It's a standardized answer to two questions your loop was already asking, what tools exist and how do I run one.

What it buys you

Tools become deployable units. A tool in your dict shares your agent's process, Python version, dependencies, and crash domain. A tool behind an MCP server is a separate process with its own everything, rewritable in TypeScript tomorrow without your agent changing a character.

Discovery replaces documentation. list_tools() returns name, description, and input schema straight from the running server. Add a tool server-side and your agent sees it on the next connection. The schema-as-prompt-engineering lesson still applies; it just moves, because now the server author owns the description that steers your model.

Trust boundaries become explicit. You've treated the tool boundary as a trust boundary since calculate refused to eval. MCP makes it a process boundary with a wire protocol across it, which is where an architect can actually enforce things: what a server can see, what its process can reach, what happens when it dies. A dict entry can't be sandboxed. A subprocess can.

The supply-chain caution

An MCP server is a dependency whose tool descriptions enter your model's context and whose results arrive wearing the authority of trusted tool output. A malicious or compromised server is the retrieved-content injection problem with a vendor logo. Connecting to a server is trusting its author; the protocol standardizes the plumbing, not the trustworthiness of what flows through it.

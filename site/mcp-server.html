Building an MCP Server

A real MCP server in about twenty lines, serving one tool over the actual wire protocol as a separate process. Plus the one place the SDK's behavior diverges from what its docs imply, which you only find by testing against a live server.

Builds on: where MCP fits. Needs: Python 3.10+ and pip install mcp (see the version trap). Full file: the server checkpoint.

The server

Create mcp_weather_server.py next to your agent. This is the complete file, not an excerpt:

from mcp.server import MCPServer

mcp = MCPServer(
    "WeatherServer",
    instructions="Provides current weather lookups for a small set of cities.",
)

FAKE_WEATHER = {
    "austin": {"temp_f": 101, "condition": "sunny"},
    "seattle": {"temp_f": 68, "condition": "cloudy"},
    "new york": {"temp_f": 84, "condition": "humid"},
}


@mcp.tool()
def get_weather(city: str) -> dict:
    """Get the current weather for a city."""
    return FAKE_WEATHER.get(city.lower(), {"temp_f": 75, "condition": "unknown"})


if __name__ == "__main__":
    mcp.run()  # stdio by default — blocks, waiting for a client on stdin

Fake data deliberately: a real weather API would add an HTTP dependency and an API key to a page that's about neither. The interesting part is the plumbing, and fake data keeps it legible.

Three moves, and what you're not writing

MCPServer(...) declares the server. The instructions string is server-level context a client can surface to its model: a system-prompt fragment authored by the tool provider. One more place where description text is quietly prompt engineering.

@mcp.tool() is the entire registration story, and the omission is the point. In Part 1, every tool cost you a hand-typed JSON Schema block: name, description, properties, required fields. Here the SDK derives all of it by introspection: function name becomes the tool name, docstring becomes the description, type hints (city: str) become the parameter schema.

Takeaway

The TOOL_SCHEMAS half of bilateral integration work just became the server's job, done by a decorator. When the client calls list_tools(), the schema it receives is what this decorator generated.

mcp.run() serves over stdio: JSON-RPC in on stdin, responses out on stdout. Stdio is what makes the local case clean, with no port, no TLS, no auth story, because the client owns the subprocess and its pipes. A remote server swaps this for HTTP transport; the tool code above it doesn't change.

Run it by hand, once

python3 mcp_weather_server.py

What you want here is an anticlimax: no import errors, no traceback, then nothing. The process sits blocked on stdin, waiting for a client to speak the protocol handshake. It'll wait forever; Ctrl+C to exit.

Not a hang

Silence plus no traceback equals a working stdio server. Knowing that saves you from "it's frozen, something's broken" the first time. From the next page on, your agent spawns this file as a subprocess and speaks the handshake for you.

The gotcha: verify the result shape against a live server

When a client calls a tool, the MCP result object offers two payload carriers: content (a list of content blocks) and structured_content (a parsed structured value). The SDK's happy-path examples read as though returning a dict populates structured_content.

The real contract

A plain -> dict return type does not populate structured_content. It comes back None, and your dict gets JSON-serialized into a text content block: a string that merely looks like your data. Only a Pydantic BaseModel return type (or an explicitly declared output schema) produces populated structured_content.

This matters because of who's downstream. Tool results flow into json.dumps and then into the model's context. Pass the raw text block through as if it were the value and nothing crashes; the model just receives a JSON string inside a JSON string, quotes escaped, and gets measurably worse at reading it. The client on the next page handles the real contract explicitly.

The habit

This came from calling the live server and inspecting the actual result object, not from the documentation. The docs describe the happy path; the running system defines the contract. Same move as verifying Granite Guardian's score tag against live output. Ten minutes with a live endpoint beats an afternoon debugging an assumption.

Why not just return a Pydantic model and take the happy path? Because your client shouldn't assume every MCP server it meets was written by someone who did. The parse-the-text fallback is what makes your client robust to the servers you didn't write, which is the entire point of speaking a standard protocol.

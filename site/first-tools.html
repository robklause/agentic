Your First Tools

Two tools make the loop run: a calculator and a comparator. The second one looks redundant until you see the failure it closes, and that failure teaches the design rule behind every guardrail in this series.

Builds on: the loop. Produces: the first runnable agent (checkpoint: chapter 3).

A tool is two things

Every tool is exactly two artifacts: an implementation (a plain Python function) and a schema (a JSON description). Keep the split sharp: the model never sees your code. The schema is the model's entire knowledge of what a tool does.

Takeaway

The schema's description field is prompt engineering, not documentation. The difference between a tool used correctly and a tool ignored can live entirely in that string.

Tool 1: calculate

LLMs are unreliable at arithmetic. Not incapable; unreliable, which is worse: the wrong answer arrives with the same fluent confidence as the right one. The general rule: if a computation has a correct answer, take it out of the model's hands and put it in a tool.

import operator

def calculate(expression: str) -> dict:
    """Evaluate a basic arithmetic expression safely (no eval of arbitrary code)."""
    import ast  # operator is already imported at module scope

    ops = {
        ast.Add: operator.add,
        ast.Sub: operator.sub,
        ast.Mult: operator.mul,
        ast.Div: operator.truediv,
        ast.Pow: operator.pow,
        ast.USub: operator.neg,
    }

    def _eval(node):
        if isinstance(node, ast.Constant):
            return node.value
        if isinstance(node, ast.BinOp):
            return ops[type(node.op)](_eval(node.left), _eval(node.right))
        if isinstance(node, ast.UnaryOp):
            return ops[type(node.op)](_eval(node.operand))
        raise ValueError("unsupported expression")

    try:
        result = _eval(ast.parse(expression, mode="eval").body)
        return {"result": result}
    except Exception as e:
        return {"error": str(e)}

Two decisions worth a sentence each:

  • AST walk, never eval(). The expression comes from the model, and the model's input comes from the user. That's a chain of untrusted input, and eval() on untrusted input is code execution. The tool boundary is a trust boundary, starting now.
  • Errors return as data, never raise. A raised exception kills your loop. An {"error": ...} dict goes back to the model, which can read it and recover. The model can't catch exceptions.

Tool 2: compare, and why it exists

The problem

Give the model only calculate and ask "is Austin's temperature more than 3 times as warm as Seattle's?" It dutifully calls calculate("3 * 68"), gets 204, and then silently eyeballs whether 101 exceeds 204 in its own head while writing the answer. It computed the product with a tool and did the comparison on vibes.

The design

A dedicated compare tool takes the remaining judgment away too. When you delegate a computation, audit what judgment stays on the model's side of the handoff; "compute 3 × 68" and "decide whether 101 exceeds 204" feel like one operation and are two.

def compare(a: float, b: float, operator_: str) -> dict:
    """Compare two numbers so the model never has to judge magnitude itself."""
    ops = {
        ">": operator.gt,
        "<": operator.lt,
        ">=": operator.ge,
        "<=": operator.le,
        "==": operator.eq,
        "!=": operator.ne,
    }
    if operator_ not in ops:
        return {"error": f"unsupported operator {operator_!r}, use one of {list(ops)}"}
    return {"result": ops[operator_](a, b)}

Trivial code, durable lesson: every guardrail in Part 2 is this same move at larger scale, finding a judgment the model is quietly making and taking it away.

The schemas

The model-facing half, sent as tools=TOOL_SCHEMAS on every call. Compare the two descriptions: calculate gets one flat sentence, compare gets escalating explicit instruction, because models reach for calculators naturally but don't naturally believe magnitude judgment is beyond them.

TOOL_SCHEMAS = [
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "Evaluate a basic arithmetic expression, e.g. '(3 + 5) * 2'.",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {"type": "string"},
                },
                "required": ["expression"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "compare",
            "description": (
                "Compare two numbers with an operator and return true/false. "
                "Use this for ANY magnitude judgment — 'is X more than Y', "
                "'is X at least Y', 'is X equal to Y', etc. Do not judge "
                "comparisons yourself; always call this tool instead."
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "a": {"type": "number"},
                    "b": {"type": "number"},
                    "operator_": {
                        "type": "string",
                        "enum": [">", "<", ">=", "<=", "==", "!="],
                        "description": "Comparison to apply as: a <operator_> b",
                    },
                },
                "required": ["a", "b", "operator_"],
            },
        },
    },
]

The enum on operator_ is the same instinct in schema form: declare the six legal values so malformed calls mostly don't happen, instead of mostly getting caught.

Dispatch, and the system-prompt reinforcement

TOOL_IMPLEMENTATIONS = {
    "calculate": calculate,
    "compare": compare,
}

A dict from name to callable. In Part 3, this dict becomes one of two places a call can route, and the fact that dispatch is this dumb is exactly why that change will be small.

The system prompt pushes from the other side (a local 9B model follows instructions less reliably than a frontier model, so the rule lives in both places the model looks):

You are a helpful assistant. Use tools when they help answer the question.
Never trust your own math — if a calculation is needed, always call the
calculate tool for it. Never judge a comparison yourself either — for
anything like 'is X more than Y' or 'is X at least Y', always call the
compare tool and use its result, rather than deciding in your head.
Takeaway

These are requests, not guarantees. The model can ignore every word, and sometimes does. The recurring hierarchy: prompts reduce a failure rate, structure eliminates a failure mode. This page built one of each (the prompt above; the AST allowlist in calculate).

Run it

Grab the complete runnable file from code checkpoints (chapter 3) and run it with a question that needs both tools:

USER: If I have 12 apples and give away a third of them, then buy 7 more, how many do I have?
--- turn 0: executing tool ---
    calculate({'expression': '12 / 3'}) -> {'result': 4.0}
...

The trace is the product here, not the apple count. You're watching a model decide, turn by turn, that it needs your code, and from here on the trace is how you'll debug everything.

What Is an Agentic Loop

An agent is a loop that lets the model ask your code for things. The model proposes a tool call, your code runs it, the result goes back into the conversation, and it repeats until the model answers in text. That's the entire mechanism behind "agentic" behavior. This page shows the loop in about 40 lines.

Builds on: Setup (Ollama serving, chat model pulled). Produces: the loop skeleton the whole series grows.

One model call, no tools

Strip everything away and an LLM interaction is one request: a list of messages in, one message back.

from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODEL = "qwen3.5:9b"   # on Apple Silicon: "qwen3.5:9b-mlx"

response = client.chat.completions.create(
    model=MODEL,
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "What's 3 times 68?"},
    ],
)
print(response.choices[0].message.content)

Two things about this shape matter more than they look.

The API is stateless. The server keeps nothing between calls. Every request resends the full history, and the model's entire sense of "what has happened" is the messages list. This is what people mean by the context window: the bounded conversation the model can see at once. It has consequences you'll hit when tool results start bloating the list.

The model only knows what it memorized in training. Live weather, today's date, your company handbook: it will refuse, or worse, guess fluently. The fix isn't a smarter model. It's giving the model a way to ask your code.

What a tool call looks like on the wire

Tool calling: alongside your messages, you send tool descriptions in JSON Schema. The model can't execute anything. What it can do is reply with a structured request instead of prose:

{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\": \"Austin\"}"
      }
    }
  ]
}

No answer text; content is null. The model is asking your code to run get_weather(city="Austin") and report back. (A weather tool is the classic example for the shape; you'll build a real one in Part 3. The first tools you actually write are a calculator and a comparator.)

Three details you'll code against: arguments is a JSON string, so you json.loads it. The id ties your eventual result back to this specific request. And this response is the seam of the whole series: everything later, guardrails, MCP, plugs into the moment between "the model asked for a tool call" and "run it."

The loop

Handle that response in a loop and you have an agent. (This is the teaching version; TOOL_SCHEMAS and TOOL_IMPLEMENTATIONS arrive on the next page, which makes it runnable.)

import json

def run_agent(user_prompt: str, max_turns: int = 5, verbose: bool = True) -> str:
    messages = [
        {"role": "system", "content": "You are a helpful assistant. "
         "Use tools when they help answer the question."},
        {"role": "user", "content": user_prompt},
    ]

    for turn in range(max_turns):
        response = client.chat.completions.create(
            model=MODEL,
            messages=messages,
            tools=TOOL_SCHEMAS,   # the JSON Schema list — next page
        )
        message = response.choices[0].message

        # Case 1: model is done — it returned a normal text answer.
        if not message.tool_calls:
            return message.content

        # Case 2: model wants to call one or more tools.
        # Append the assistant's request first — the API requires it
        # before the matching tool result messages.
        messages.append(message)

        for call in message.tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments)

            # >>> the seam: everything later plugs in here <<<
            impl = TOOL_IMPLEMENTATIONS.get(name)   # dispatch dict — next page
            result = impl(**args) if impl else {"error": f"unknown tool {name}"}

            if verbose:
                print(f"--- turn {turn}: {name}({args}) -> {result}")

            # Feed the result back as a "tool" message tied to this call id.
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": json.dumps(result),
            })

    return "Hit max_turns without a final answer."

Read the exit conditions; they're the design

The loop ends two ways: the model returns a message with no tool_calls (your answer), or max_turns runs out. The cap isn't decoration. A model can request tool call after tool call forever, and without a limit that's an infinite loop burning compute.

Later, Guardrails That Compose meets a subtler version of this failure (a model reformulating the same fruitless search five ways) and builds sharper backstops. The blunt cap stays anyway. Defense in depth starts here.

Notice what the loop does not do: no parsing prose for intent, no regexing answers out of text, no state beyond the message list. The list is the agent's entire memory; the structured tool_calls field is the entire protocol. That austerity is why this loop, unchanged, later drives tools it discovers at runtime from a separate process.

Why "agentic" is just this

Takeaway

There is no separate agent runtime, no planner module, no hidden reasoning engine. Frameworks selling "agent orchestration" are selling this loop with configuration on top. When you know the loop, framework docs stop being magic words and become a map of where someone else put their guardrails and dispatch.

That's not a dismissal of frameworks (see how to evaluate them). It's a claim about understanding: you'll judge those products by asking where the seam is, because you'll know there has to be one.
